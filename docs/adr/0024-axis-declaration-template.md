# ADR-0024: Axis Declaration Template for Multi-Value Fields

- Status: Draft
- Date: 2026-04-30
- Supersedes: —
- Superseded by: —
- Related: ADR-0023 (the originating example), ADR-0015 (dataflow access modes — retroactively axis-shaped)

## Context

ADR-0023 introduced an *axis* — a typing dimension along which every value of a multi-value field must be classified — for `Edge.edge_type`, naming three sections (`relationship`, `endpoint_shape`, `pending_classification`) and codifying the axiom that every value should name the relationship between src and dst. The implementation produced four artifacts in close succession:

- A registry module: `packages/hypergumbo-core/src/hypergumbo_core/edge_types.py` (PR #3459).
- A by-axis view: `docs/concept-axes.md` regenerated by `scripts/generate-concept-axes` (PR #3463).
- A drift linter: `scripts/check-edge-type-drift` wired into pre-commit (PR #3462).
- A property test: `find_axis_drift` plus the in-tree subset assertion in `test_edge_types.py` (PR #3459, refactored in PR #3462).

Each artifact rhymes with the others — the registry is the source of truth, the view is its human-readable presentation, the linter and the test are two surfaces of the same drift detection. The pattern is reusable. Other multi-value fields almost certainly need it: `Symbol.kind` (~50 values; the audit playbook's adjacent-concept-sweep step explicitly names this as next), `evidence_type` (surfaced as a leakage source during PR #3459 — a value belonging to this field was smuggled into a set checked against `edge_type`), `supply_chain.tier`, the access-mode-annotated edges from ADR-0015 (which arguably already constitute an axis though it was never declared as one).

The cost of not having a template: each new axis declaration re-derives the same shape from scratch, accumulating subtle inconsistencies (registry lives here vs. there; linter named this convention vs. that; the by-axis view is markdown vs. a JSON-Schema extension key vs. a generated table). Consumers then fragment around the inconsistencies. The audit-lifecycle session (Apr 2026) surfaced the question "what other fields need this treatment?" and the answer is "we don't know yet, but every time we find one, we shouldn't reinvent the wheel."

The cost of having a template that's wrong: the template becomes ritual. Future axis declarations follow the template even when the field's nature doesn't fit, producing artifacts that nobody uses. The template must be tight enough to be reusable and loose enough to admit fields whose enforcement story differs (e.g., a tiny enum with three values may not need a registry module at all).

## Decision

The axis declaration template is **four parts**, each independently namable and each grounded in the ADR-0023 instance.

### 1. Axis name

A stable identifier for the axis itself, distinct from the field name. The field is `Edge.edge_type`; the axis is *the edge-type axis*. Multiple axes can in principle apply to the same field — though in practice we've seen one-axis-per-field, and the template assumes this default.

The axis name appears in:
- Module-level constants in the registry (e.g., `AXIS_RELATIONSHIP`, `AXIS_ENDPOINT_SHAPE`, `AXIS_PENDING`).
- The by-axis view's section headings.
- The originating ADR's title or first paragraph.

### 2. Axiom

The single sentence that defines the axis. Every value classified on the axis must satisfy the axiom; values that violate the axiom are deprecation candidates.

ADR-0023's axiom: *"`edge_type` names the relationship that produced the edge. Properties of either endpoint are queried from the endpoint. Other properties of the relationship go in `edge.meta` (or a dedicated `Edge` field, when warranted)."*

Properties of a good axiom:

- **Falsifiable** — given a candidate value, the axiom either accepts it or rejects it. ADR-0023's axiom rejects `native_bridge` (the `bridge` part is endpoint shape, not the relationship).
- **One-sentence-long** — if the axiom needs a paragraph, the axis is doing too much.
- **Distinguishes the axis-conformant section from the rest** — the axiom is what makes some values `relationship` and others `endpoint_shape`.

Some axes will have *sections* — sub-classifications within the axis (relationship, endpoint_shape, pending_classification on `Edge.type`). Sections are a property of the registry, not of the axiom; the axiom defines the canonical section, and other sections are deprecation-candidate or pending-audit buckets.

### 3. Consumer pattern

The accessor function shape that consumers use to query the axis. Without this, consumers reinvent the access pattern with hardcoded sets and the registry's value drifts from the consumer-side enumeration (the silent-bug pattern from ADR-0023 §1).

ADR-0023's consumer pattern: `edge_types_on_axis(axis: str) -> tuple[EdgeTypeSpec, ...]`. Consumers needing "all relationship-shaped edge types" call `edge_types_on_axis(AXIS_RELATIONSHIP)` instead of maintaining `_STRUCTURAL_EDGE_TYPES = {...}` locally.

The accessor signature should be predictable across axes:
- `<field>_on_axis(axis: str) -> tuple[<spec_type>, ...]` — the canonical form.
- Values returned are typed objects (`EdgeTypeSpec`) carrying name + axis + description, not raw strings — this preserves the ability to add per-value metadata without breaking callers.
- The accessor is colocated with the registry module.

### 4. Enforcement

A drift-detection mechanism, mandatory. Without enforcement, the axiom decays into folklore. ADR-0023's enforcement is two-layered:

- **Static (in-tree)**: an AST walker (`find_axis_drift`) finds module-level `*EDGE_TYPE*`-named sets in `packages/` and asserts their values are subsets of the canonical registry. Surfaces in two places: a property test in `test_edge_types.py` (CI gate) and a CLI script `scripts/check-edge-type-drift` (pre-commit gate).
- **Runtime (planned)**: ADR-0023 §3 reserves a corpus-based test that asserts the axis holds against actual emitted edges from a representative analysis run. Not yet built; counts as a known gap.

The enforcement pattern transfers cleanly:
- Static walker — adapt the name-substring filter (`EDGE_TYPE` → `KIND` for `Symbol.kind`, etc.).
- Pre-commit hook entry — copy the existing one.
- Property test — copy and rename.

For very small axes (single-digit-value enums), the static linter may be overkill and a single property test is enough. Use judgment.

### Declaration workflow

Adding a new axis to the codebase follows seven steps. Steps 1–4 are mandatory; 5–7 ship with the first migration that exercises the axis.

1. **Open a numbered ADR** using this template's structure: Context (why), Decision (the four parts), Likely-deprecate list (first cut, refinable by audit), Migration plan (phases for renaming or folding values), Related (back-references).
2. **Land a registry module** at `packages/<package>/src/<module>/<field>_types.py` (or extend an existing one) with the four-part scaffolding: `AXIS_*` constants, `<TypeName>Spec` frozen dataclass (name + axis + description), tuple-of-specs `<FIELD>_TYPES`, accessors (`all_*_names()`, `*_on_axis(axis)`, `find_*(name)`).
3. **Land a drift-coherence linter** at `scripts/check-<field>-drift` reading the registry and AST-walking `packages/` for `*<FIELD-PREFIX>*`-named sets. Wire into `.githooks/pre-commit` skipping when no `packages/*.py` files are staged.
4. **Land a property test** in the registry's package's `tests/` directory: registry invariants (no duplicates, every spec has a valid axis, etc.) plus a drift-detection test calling the linter's underlying function on the live tree.
5. **Land a by-axis view** at `docs/concept-axes.md` (existing aggregator; extend `scripts/generate-concept-axes`'s `_SECTIONS` table with the new axis's sections). Wire freshness check into pre-commit if it isn't already there.
6. **Update the audit playbook** at `.agent/agent_playbooks_protocols_sops_skills/what-if-we-dont-know-what-the-fuck-we-are-talking-about-audit-aka-fundamental-concept-audit.md` to mention the new field as audited; remove from the Step 5 adjacent-concept-sweep TODO list if applicable.
7. **(Optional) Migrate violators**: if pre-existing values violate the new axiom, follow ADR-0023's four-phase migration shape (consumers → producers → schema bump → deprecation removal).

### Creation practice

Any PR that adds a multi-value field to a core dataclass (`Edge`, `Symbol`, `Span`, `AnalysisRun`, anything in `ir.py` or `datamodels.py`) must answer: *what axis does this field occupy?* The answer is one of:

- **Single-value or small bounded enum** — no axis declaration needed; document the enumeration in the dataclass docstring.
- **An existing axis applies** — reuse the existing registry; cite the ADR.
- **A new axis is needed** — open a new ADR using this template, land the four artifacts.

Surface the practice via:

- **Documentation** — AGENTS.md gets an essentialization referencing this ADR; the audit playbook's Step 6 Document outcome already mentions the registry shape and is updated to point here.
- **(Future)** A pre-commit prompt or PR-template question detecting new multi-value field declarations on core dataclasses. Out of scope for the initial template landing; tracker-able as a follow-on if the documentation channel proves insufficient.

## Consequences

### Positive

- **Composability**: future axes inherit four artifacts plus a workflow, reducing axis declaration from "design-from-scratch" to "fill in the template."
- **Tooling reuse**: the linter pattern, the property-test pattern, and the by-axis-view generator are all parameterizable. The next axis adds a section to `generate-concept-axes`'s `_SECTIONS`, not a parallel doc.
- **Audit ergonomics**: the Fundamental Concept Audit playbook's Step 5 (adjacent concept sweep) gains a structural target — "what fields haven't yet declared an axis?" becomes actionable rather than open-ended.
- **Surface area for the cadence hook**: each declared axis is a candidate suspect domain for the next periodic audit pass.

### Negative

- **Overhead for trivial axes**: a 3-value enum with no contested classifications doesn't benefit from a registry module + linter + view. The "use judgment" carveout in §4 (Enforcement) addresses this but relies on the author's calibration.
- **Template ossification risk**: future axis-shaped fields whose enforcement story doesn't fit the template (e.g., values that legitimately span sections, or fields where drift is benign) may end up bent into the template's shape rather than the template being widened. Mitigation: the audit playbook is the place to surface "the template doesn't fit here, why?" and propose template amendments.

### Risks

- **The template becomes ritual**: future ADRs cite ADR-0024 without actually following the discipline. Mitigation: the four enforcement artifacts (registry, linter, view, test) are mechanically detectable; reviewing a new axis ADR includes asking "where are the four artifacts?"
- **Sectioning mismatches**: an axis whose violators don't cleanly fit `endpoint_shape` / `pending_classification` may produce ad-hoc section names that don't compose. Mitigation: section vocabulary is per-axis; sections aren't required to match across axes.

## Worked example: Edge.type per ADR-0023

| Template part | ADR-0023 instance |
|---|---|
| Axis name | the edge-type axis (with sections `relationship`, `endpoint_shape`, `pending_classification`) |
| Axiom | "`edge_type` names the relationship that produced the edge…" (ADR-0023 §"Decision") |
| Consumer pattern | `edge_types_on_axis(axis: str) -> tuple[EdgeTypeSpec, ...]` in `hypergumbo_core.edge_types` |
| Enforcement | static `find_axis_drift` (CI gate at `test_edge_types.py`, pre-commit gate at `scripts/check-edge-type-drift`); runtime corpus test reserved per ADR-0023 §3 |

Workflow steps landed across PRs #3459 (registry + property test), #3462 (linter + pre-commit), #3463 (by-axis view), with playbook updates folded into the cadence-hook PR (#3460) and discrepancy resolutions in PR #3464.

## Alternatives considered

### A. Status quo — no template

Each new axis re-invents the four-part scaffolding. Loses the registry-module convention, the accessor signature, the linter shape, the by-axis view aggregator. Downsides: fragmentation; the audit playbook's adjacent-concept-sweep step has nothing concrete to point at; future contributors have no shape to follow.

### B. One mega-ADR per host dataclass

`Edge.* axes`, `Symbol.* axes`, `Span.* axes`. Wider scope per ADR, but each is a very different conversation (Edge values are framework-derived; Symbol kinds are language-derived; Span values are positional). Bundling them produces ADRs that are hard to amend without touching unrelated material. Rejected in favor of the per-axis ADR pattern (one ADR-0023, future ADR-0025 etc., each citing this template).

### C. Code-generated axes from declarative DSL

Define each axis in a YAML or TOML file; generate the registry module, the linter, and the view from one source. Tempting but premature — we have one example, soon two; YAML-first is over-engineering for that volume. Revisit if the template ships five axes without the per-axis Python registry feeling redundant.

## Open questions (Draft status)

1. **Should ADR-0015 (dataflow access modes) be retroactively documented as the first axis instance?** The access-mode field on `Edge` predates ADR-0023 and arguably constitutes an axis already (with values `read`, `write`, `read_write`, etc.). The four template artifacts don't currently exist for it. Decision: leave as-is until a separate audit confirms whether retroactive registry-ization is worth the disruption.
2. **Pre-commit detection of new multi-value field additions** — the creation practice currently relies on documentation. Worth automating? Detection requires AST inspection of `@dataclass` definitions for fields whose type narrows (Literal vs. str), or a manual hint annotation. Tracker as a follow-on if drift surfaces.
3. **Section vocabulary normalization** — ADR-0023 used `relationship` / `endpoint_shape` / `pending_classification`. Future axes will pick their own; should there be a recommended vocabulary (`canonical` / `deprecated` / `pending_audit`) that future ADRs are encouraged to reuse? Probably yes for the canonical / deprecated split; pending_audit is more axis-specific.
